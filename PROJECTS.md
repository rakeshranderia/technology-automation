# Projects

Standalone projects should be created only when an artefact can be understood or used independently.

## When Something Becomes a Project

A project should normally have:

- a clear problem statement;
- a usable output or working capability;
- its own README;
- setup or usage instructions;
- examples or screenshots where useful;
- a defined audience;
- enough substance to stand independently.

## What Should Stay a Toolkit

Keep material inside a toolkit when the value comes from several related references, templates or scripts working together.

## Project Candidates

Strong future project candidates are likely to come from:

- interactive assessment tools;
- automation suites with multiple scripts;
- reporting or analysis tools;
- deployable proofs of concept;
- end-to-end utilities with clear inputs and outputs.

Do not create a separate repository simply to increase repository count.

## Portfolio Principle

**Toolkits demonstrate breadth and repeatable practice.  
Projects demonstrate independently usable capability.**
